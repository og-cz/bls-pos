# Progress

Short demo notes at the end of each phase.

## Phase 0 — Foundation (2026-10-29)

**Demo:** `pnpm install && pnpm dev` → open the printed URL. The page shows
"Hello, Bilis POS" and **API: online**, fetched from `GET /api/v1/health` on the same
Worker. Deep links like `/some/route` fall back to the SPA. Unknown `/api/v1/*` paths
return a JSON `NOT_FOUND` error.

**Checks passing locally:** `pnpm lint`, `pnpm format:check`, `pnpm typecheck`,
`pnpm test` (2 API tests in workerd), `pnpm build` (sell-screen JS 81 KB gzipped,
budget 200 KB).

**Not yet done (needs the owner):**

- Push to GitHub so CI runs (`.github/workflows/ci.yml`).
- Preview deploy: `pnpm exec wrangler login`, then `pnpm deploy`. Needs a Cloudflare account.

**Deviations from the plan:**

- TypeScript 6.0 instead of 7.0 (typescript-eslint doesn't support 7 yet).
- `@cloudflare/vitest-plugin` instead of `@cloudflare/vitest-pool-workers` (renamed upstream).
- `worker-configuration.d.ts` is generated by `wrangler types` and committed. CI fails
  if it's stale.

## Phase 1 — Database and authentication (2026-10-29)

**Demo:** `pnpm db:migrate:local && pnpm dev`, then open `/signup`.

1. Create a shop. The shop code fills itself in from the shop name. The Turnstile
   check uses Cloudflare's always-pass test key in development.
2. The 10 recovery codes appear once, with Download, Print and Copy. **Continue** only
   unlocks after you tick "I saved these codes".
3. The home screen shows the shop and who is logged in. **Log out** goes to `/login`,
   with the shop code already filled in.
4. Get the password wrong 3 times and a Turnstile check appears. After 5 wrong tries
   the account is rate limited (429), and after 10 it is locked for 15 minutes.
5. At `/recover`, enter a recovery code (any case, spaces are fine) and a new password.
   The owner is logged in again, every other device is logged out, and the screen
   shows how many codes are left.

**Checks passing locally:** lint, format, typecheck, 90 API tests in workerd (hashing,
sessions, rate limits, lockout, Turnstile, recovery, including two requests racing
for one code), `vite build` (JS 111 KB gzipped, budget 200 KB).

**Carried into later phases:**

- Admins get an in-app notice when an account locks (needs the audit log, Phase 2).
- Staff password reset by an admin (Phase 2 staff work).
- The app follows the system dark mode once the theme engine lands (Phase 6). The dark
  palette and the logo's dark color already exist.

**Notes:**

- Recovery codes are random, so they are stored as HMAC-SHA256 with the pepper instead
  of PBKDF2. That keeps Worker CPU low, and a stolen database alone still can't check
  guesses.
- Production builds need `VITE_TURNSTILE_SITE_KEY` (see `.env.example`). Without it the
  security check shows an error and signup is refused (it fails closed).
- The web app uses a ~40-line History API router (`src/client/lib/router.ts`) instead
  of a router library. Five screens don't need one.
- The Bilis POS logo is `public/logo.svg` (also the favicon), in a fixed blue
  `--brand-mark` color that shop themes don't change.

## Phase 2 — Tenancy, roles and staff (2026-10-29)

**Demo:** `pnpm db:migrate:local && pnpm dev`, sign up, and you land on the dashboard
inside the app shell. That's a sidebar on a PC and a bottom tab bar on a phone.

- `POST /api/v1/staff` (owner/admin) creates a cashier with a 12-character temporary
  password, shown once. Log in as that cashier: the menu shows only **Sell** and
  **Inventory**, and opening `/staff` sends you back to Sell.
- `POST /api/v1/staff/:id/deactivate` signs the cashier out on every device at once.
- `GET /api/v1/audit` lists signups, logins (including failures and lockouts),
  recoveries and staff changes, newest first.

**Proven by tests (136 total):** every API route has a declared minimum role (a new
route without one fails CI). Every protected route refuses missing and forged
sessions. A full staff/admin/owner permission matrix passes. One shop can neither see
nor change another shop's data through any endpoint, whatever shop id the client
sends. Every post-login service takes `(db, shopId, ...)`.

**Rules implemented:** admins add and deactivate staff. Only the owner adds or
deactivates admins. Nobody can create an owner or deactivate the owner or themselves.
Free plan: up to 5 active admins + staff (the owner and deactivated accounts don't
count), from the shared `entitlements` module.

**Carried forward:**

- The Staff and Activity screens are placeholders. Their APIs are done; the screens
  come next.
- Staff can't change their temporary password yet (`POST /auth/password` is planned
  with the profile work). Reset by an admin comes with `PATCH /staff/:id`.
- The in-app notice to admins when an account locks will read the `login.locked`
  audit entries.

**Notes:** UUIDv7 ids are now monotonic within a millisecond, so audit entries keep
their true order. JS bundle 140 KB gzipped (budget 200 KB); the account menu added
Radix DropdownMenu.

## Phase 3 — Products and inventory (2026-10-30)

**Demo:** `pnpm db:migrate:local && pnpm dev`, log in as an owner.

1. **Products → Add product:** name, price in pesos (stored as centavos), optional
   cost, SKU, category (a new one can be made right there), opening stock, low-stock
   level and a photo. The photo is resized on the device to an 800 px WebP before
   upload (a 3000×2000 test image became about 4 KB).
2. The list searches on the device as you type (accent-insensitive, so "cafe" finds
   "Café Latte", or by SKU), with category chips, a **Low stock** filter and an
   **Archived** view. A table on PC, cards on phones; cost shows for admins only.
3. **Inventory:** counts of what is running low or out, **Deduct** with a required
   reason for everyone, **Restock** for admins, and the recent stock history.
4. Log in as a cashier: no cost anywhere, no Add/Restock buttons, no archived
   products, and the history shows only their own changes.

**Proven by tests (207):** the database refuses negative stock, so two cashiers taking
the last items at once can't oversell and a refused change leaves no movement behind;
stock always equals the sum of its movements. SKUs are unique per shop; categories,
products, photos and history never cross shops. Uploads accept only real JPEG/PNG/WebP
(SVG and disguised files refused), up to 2 MB, within the plan's image space. Free
limits: 500 active products, 200 MB of images.

**Carried forward:**

- The R2 bucket `bls-pos-media` must be created on Cloudflare before the first deploy.
- Product photos are private to the shop; the public storefront opens them up in Phase 6.
- JS bundle 153 KB gzipped (budget 200 KB). Route-level code splitting is planned in
  Phase 10 and may be pulled forward if the sell screen gets close to the budget.

**Notes:** tests now pin the clock to the middle of a 15-minute window, after a
login rate-limit test failed once when a run crossed a window edge.

## Phase 3.5 — Bulk import, export and backup (2026-10-30)

**Demo:** log in as an owner, open **Products → Import**.

1. Download the Excel or CSV template, or use your own sheet (headers like "Product
   Name", "Qty" and "Barcode" are understood). Choose the file or paste rows from
   Google Sheets; it is read in a Web Worker, so the page never freezes.
2. Every row is checked ("Row 214: price is missing", "SKU is also on row 2"); fix cells
   in place.
3. **Import** sends the ready rows in 250-row batches with a progress bar, retries and
   Stop. A SKU that already exists updates that product; stock in the file only sets
   opening stock for new products.
4. **Add photos in bulk:** drop photos named by SKU (`NGK-CR7.jpg`); each is matched,
   cropped to 4:3, compressed and uploaded in the background.
5. **Products → Export:** products (re-importable), stock levels or stock movements as
   Excel or CSV, or a **Full backup (.json)**. **Import → Restore from backup** runs a
   backup through the same flow after a confirmation.

**Proven by tests (249):** a 5,000-row import in 20 chunks and a full re-import as
updates; duplicate SKUs in a file; bad rows skipped with reasons; the product limit
refusing a chunk without writing anything; SKUs never crossing shops; formula-injection
protection on export; a backup restored into an empty shop gives the same products, and
restoring twice doesn't duplicate.

**Also in this phase (owner requests):** a photo beside every product, tap to view full
size; photos in two sizes (full ~100–200 KB, thumbnail ~5–25 KB); Take photo / Add
photo with a centering guide and an editor (move, zoom, rotate); Settings (theme, text
size, list/compact/tiles/large tiles, menu side, icons-only menu); hamburger in the side
menu; Free product limit raised to 5,000; the app is written "bls POS".

**Notes:**

- Exports and backups are built in the browser from the paged API (logged via
  `POST /audit/exports`), because the free plan gives a request only 10 ms of CPU.
- Import batches send each list as one JSON value read with `json_each`: about 8 queries
  per 250 rows. A 5,000-product import uses roughly 10–15% of the 100,000 daily D1 row
  writes shared by every shop on the deployment.
- Backups leave out staff accounts on purpose.
- Live camera capture is untested on a real device so far.
