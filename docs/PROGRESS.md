## Phase 1 — Database and authentication (2026-10-29)

**Demo:** `pnpm db:migrate:local && pnpm dev`, then open `/signup`.

1. Create a shop. The shop code fills itself in from the shop name. The Turnstile
   check uses Cloudflare's always-pass test key in development.
2. The 10 recovery codes appear once, with Download, Print and Copy. **Continue** only
   unlocks after you tick "I saved these codes".
3. The home screen shows the shop and who is logged in. **Log out** goes to `/login`,
   with the shop code already filled in.
4. Get the password wrong 3 times and a Turnstile check appears. After 5 wrong tries
   the account is rate limited (429), and after 10 it is locked for 15 minutes.
5. At `/recover`, enter a recovery code (any case, spaces are fine) and a new password.
   The owner is logged in again, every other device is logged out, and the screen
   shows how many codes are left.

**Checks passing locally:** lint, format, typecheck, 90 API tests in workerd (hashing,
sessions, rate limits, lockout, Turnstile, recovery, including two requests racing
for one code), `vite build` (JS 111 KB gzipped, budget 200 KB).

**Carried into later phases:**

- Admins get an in-app notice when an account locks (needs the audit log, Phase 2).
- Staff password reset by an admin (Phase 2 staff work).
- The app follows the system dark mode once the theme engine lands (Phase 6). The dark
  palette and the logo's dark color already exist.

**Notes:**

- Recovery codes are random, so they are stored as HMAC-SHA256 with the pepper instead
  of PBKDF2. That keeps Worker CPU low, and a stolen database alone still can't check
  guesses.
- Production builds need `VITE_TURNSTILE_SITE_KEY` (see `.env.example`). Without it the
  security check shows an error and signup is refused (it fails closed).
- The web app uses a ~40-line History API router (`src/client/lib/router.ts`) instead
  of a router library. Five screens don't need one.
- The Bilis POS logo is `public/logo.svg` (also the favicon), in a fixed blue
  `--brand-mark` color that shop themes don't change.

## Phase 2 — Tenancy, roles and staff (2026-10-29)

**Demo:** `pnpm db:migrate:local && pnpm dev`, sign up, and you land on the dashboard
inside the app shell. That's a sidebar on a PC and a bottom tab bar on a phone.

- `POST /api/v1/staff` (owner/admin) creates a cashier with a 12-character temporary
  password, shown once. Log in as that cashier: the menu shows only **Sell** and
  **Inventory**, and opening `/staff` sends you back to Sell.
- `POST /api/v1/staff/:id/deactivate` signs the cashier out on every device at once.
- `GET /api/v1/audit` lists signups, logins (including failures and lockouts),
  recoveries and staff changes, newest first.

**Proven by tests (136 total):** every API route has a declared minimum role (a new
route without one fails CI). Every protected route refuses missing and forged
sessions. A full staff/admin/owner permission matrix passes. One shop can neither see
nor change another shop's data through any endpoint, whatever shop id the client
sends. Every post-login service takes `(db, shopId, ...)`.

**Rules implemented:** admins add and deactivate staff. Only the owner adds or
deactivates admins. Nobody can create an owner or deactivate the owner or themselves.
Free plan: up to 5 active admins + staff (the owner and deactivated accounts don't
count), from the shared `entitlements` module.

**Carried forward:**

- The Staff and Activity screens are placeholders. Their APIs are done; the screens
  come next.
- Staff can't change their temporary password yet (`POST /auth/password` is planned
  with the profile work). Reset by an admin comes with `PATCH /staff/:id`.
- The in-app notice to admins when an account locks will read the `login.locked`
  audit entries.

**Notes:** UUIDv7 ids are now monotonic within a millisecond, so audit entries keep
their true order. JS bundle 140 KB gzipped (budget 200 KB); the account menu added
Radix DropdownMenu.

## Phase 3 — Products and inventory (2026-10-30)

**Demo:** `pnpm db:migrate:local && pnpm dev`, log in as an owner.

1. **Products → Add product:** name, price in pesos (stored as centavos), optional
   cost, SKU, category (a new one can be made right there), opening stock, low-stock
   level and a photo. The photo is resized on the device to an 800 px WebP before
   upload (a 3000×2000 test image became about 4 KB).
2. The list searches on the device as you type (accent-insensitive, so "cafe" finds
   "Café Latte", or by SKU), with category chips, a **Low stock** filter and an
   **Archived** view. A table on PC, cards on phones; cost shows for admins only.
3. **Inventory:** counts of what is running low or out, **Deduct** with a required
   reason for everyone, **Restock** for admins, and the recent stock history.
4. Log in as a cashier: no cost anywhere, no Add/Restock buttons, no archived
   products, and the history shows only their own changes.

**Proven by tests (207):** the database refuses negative stock, so two cashiers taking
the last items at once can't oversell and a refused change leaves no movement behind;
stock always equals the sum of its movements. SKUs are unique per shop; categories,
products, photos and history never cross shops. Uploads accept only real JPEG/PNG/WebP
(SVG and disguised files refused), up to 2 MB, within the plan's image space. Free
limits: 500 active products, 200 MB of images.

**Carried forward:**

- The R2 bucket `bls-pos-media` must be created on Cloudflare before the first deploy.
- Product photos are private to the shop; the public storefront opens them up in Phase 6.
- JS bundle 153 KB gzipped (budget 200 KB). Route-level code splitting is planned in
  Phase 10 and may be pulled forward if the sell screen gets close to the budget.

**Notes:** tests now pin the clock to the middle of a 15-minute window, after a
login rate-limit test failed once when a run crossed a window edge.

## Phase 3.5 — Bulk import, export and backup (2026-10-30)

**Demo:** log in as an owner, open **Products → Import**.

1. Download the Excel or CSV template, or use your own sheet (headers like "Product
   Name", "Qty" and "Barcode" are understood). Choose the file or paste rows from
   Google Sheets; it is read in a Web Worker, so the page never freezes.
2. Every row is checked ("Row 214: price is missing", "SKU is also on row 2"); fix cells
   in place.
3. **Import** sends the ready rows in 250-row batches with a progress bar, retries and
   Stop. A SKU that already exists updates that product; stock in the file only sets
   opening stock for new products.
4. **Add photos in bulk:** drop photos named by SKU (`NGK-CR7.jpg`); each is matched,
   cropped to 4:3, compressed and uploaded in the background.
5. **Products → Export:** products (re-importable), stock levels or stock movements as
   Excel or CSV, or a **Full backup (.json)**. **Import → Restore from backup** runs a
   backup through the same flow after a confirmation.

**Proven by tests (249):** a 5,000-row import in 20 chunks and a full re-import as
updates; duplicate SKUs in a file; bad rows skipped with reasons; the product limit
refusing a chunk without writing anything; SKUs never crossing shops; formula-injection
protection on export; a backup restored into an empty shop gives the same products, and
restoring twice doesn't duplicate.

**Also in this phase (owner requests):** a photo beside every product, tap to view full
size; photos in two sizes (full ~100–200 KB, thumbnail ~5–25 KB); Take photo / Add
photo with a centering guide and an editor (move, zoom, rotate); Settings (theme, text
size, list/compact/tiles/large tiles, menu side, icons-only menu); hamburger in the side
menu; Free product limit raised to 5,000; the app is written "bls POS".

**Notes:**

- Exports and backups are built in the browser from the paged API (logged via
  `POST /audit/exports`), because the free plan gives a request only 10 ms of CPU.
- Import batches send each list as one JSON value read with `json_each`: about 8 queries
  per 250 rows. A 5,000-product import uses roughly 10–15% of the 100,000 daily D1 row
  writes shared by every shop on the deployment.
- Backups leave out staff accounts on purpose.
- Live camera capture is untested on a real device so far.

## Phase 4 — Selling (2026-10-30)

**Demo:** log in (staff land on **Sell**).

1. Tap photo tiles to add (one tap = one); search by name or SKU, or use category chips.
   A USB/Bluetooth barcode scanner works from anywhere on the screen; Enter in the
   search box adds the exact SKU or the only match.
2. The cart sits beside the grid on PC/tablet and opens from a bar on phones; − / +,
   remove, clear. Items can't exceed stock.
3. **Charge ₱X** → Cash (quick amounts: Exact, next round amount, ₱500, ₱1,000; keypad;
   large change) or Other (manual, with a reference like a GCash number).
4. **Complete sale** → change in large type and the receipt (shop, number, date,
   cashier, lines, totals, payment, "not an official receipt or invoice"), with **Print**
   (receipt only, 58/80 mm or A4) and **New sale**.
5. Admins can void a sale with a reason (`POST /sales/:id/void`); the screen for it comes
   with the dashboard in Phase 5.

**Proven by tests (290):** prices only from the database (client prices, totals or shop
refused); one D1 batch per sale; overselling refused with the product named and nothing
left behind (no sale, movement or number used); two tills on the last item → one sale;
five tills at once → numbers 1–5, no gaps; the same idempotency key (retry, or three
copies at once) → one sale, stock taken once; voids restock exactly once, even two at
once, and the item can be sold again; receipts keep the price paid after a price change
and never show cost; deactivated cashiers can't sell.

**Notes:** each screen is now its own download (main bundle 100 KB gzipped, was 166 KB).
Payment methods go through `PaymentAdapter` (cash, other_manual) so Paid methods plug in
later. The receipt's "not an official receipt or invoice" wording is a placeholder for a
tax professional to confirm (Section 7.16).

## Phase 5 — Dashboard and reports (2026-10-30)

**Demo:** log in as the owner or an admin (you land on the **Dashboard**).

1. **Dashboard:** a stock alert (links to Inventory), then today's sales, transactions,
   average sale and gross profit, each with yesterday's figure. Below: sales per day for
   7 or 30 days (hover or tap a bar; **Show as table** for exact numbers), top 5
   products with photos, and sales by staff (deactivated people still listed).
2. **Sales** (menu): pick From/To days, open any sale to reprint or **Void** it with a
   reason, **Export CSV** (logged in Activity; spreadsheet formulas are neutralised).
   Staff see **My sales today**: only their own sales for their shift.
3. **Daily close** (Sales, one day picked): the Z-reading — sale number range, completed
   sales by payment method, voids, total — with **Print**. **Close day** saves it for
   good: after that the day's sales can't be voided, and if it's today, no more sales
   can be rung up until midnight.

**How it works:** days are counted in the shop's timezone (Asia/Manila by default, any
IANA zone including DST). A Cron Trigger at 00:10 Manila (`10 16 * * *` UTC) writes
`daily_summaries` for yesterday and the day before; reports read those for older days
and count today, yesterday and any missed day straight from the sales (one query, each
day's window passed as JSON). A void refreshes its day's summary at once. The dashboard
is one request of about 8 queries. Daily closings are locked by database triggers
(migration 0007): no new sales or voids inside a closed day, and no edits or deletes of
a closing — even with direct SQL.

**Proven by tests (315):** Manila day boundary at 16:00 UTC; another timezone gets its
own days; the nightly run is repeatable; voids update an old day at once; income by
day, Monday-start week and month with empty periods kept; stored, live and missed days
add up exactly; top products skip voided sales; cashier totals include voids;
staff can't see others' sales or other days; paging; Z-reading totals, payment
breakdown and number range; closed day refuses voids, second close, new sales and SQL
edits; only admins close, never a future day; every report is tenant-scoped and
admin-only.

**Notes:** reports are admin-only because they show cost and profit. The chart is plain
HTML/CSS (no chart library; the dashboard screen is 4 KB gzipped).

## Phase 6 — Branding and storefront (2026-10-31)

**Demo:** log in as the owner or an admin.

1. **Branding** (menu → Shop): pick a preset, the color wheel, or a color **From logo**;
   the whole app changes as you pick. **Look**: Automatic/Light/Dark for the shop,
   five fonts, sharp/soft/round corners. **Logo and cover photo**: pick, crop (square
   logo, 16:5 cover), upload; darken the cover with the slider. **Save** stays at the
   bottom of the screen; leaving without saving puts the old look back.
2. **My profile** (account menu): add a photo (square crop) and change your display
   name. Photos show in the menu and on the Staff list.
3. **Shop page** (menu → Shop): turn the public page on, choose to show prices and
   "Available/Sold out", write a description, then **Copy link**, **Share** or
   **Download QR** (a printable PNG with the shop name). Each product has "Show on your
   shop page" in its form.
4. Open `/s/<shop code>` signed out: cover, logo, name, description and the chosen
   products, in the shop's colors and font, with a Share button.

**How it works:** the theme is Zod-validated JSON; only those values become CSS
variables (brand scale 50–950 from OKLCH math in `src/shared/theme.ts`, no library). A
contrast guard keeps button text at 4.5:1 and buttons at 3:1 against the page, nudging
the lightness if needed. Fonts download only when a shop uses them. The public page and
its images go through `/api/v1/public/*`: off means 404 (the same as no shop), only the
logo, cover and shown products' photos are served (never avatars), prices and
availability only when chosen, never cost, exact stock or staff. Rate limited per IP
(Workers rate limiting binding, 120/min) and cached for 60 seconds. The menu is grouped
into Overview, Selling, Stock and Shop; Settings is also in the account menu.

**Proven by tests (343):** palette and contrast for every preset and 200 random colors;
theme, shop settings and profile edits refuse unknown fields, bad values and raw CSS;
staff can't change branding or the shop page; the public page leaks no cost, stock
count, hidden/archived product, username or internal id; off and missing pages look the
same; another shop's page can't reach this shop's images; reserved shop codes refused.

**Notes:** the cover's edge cache is a 60-second max-age rather than an explicit purge.
Not checked on a real phone yet: camera crop for avatars, and the share sheet.

## Phase 7 — Onboarding and help (2026-10-31)

**Demo:** sign up a new shop. After saving the recovery codes you land in **setup**:

1. **Welcome:** shop name and kind (a new kind brings its suggested colors).
2. **Make it yours:** a preset, logo and cover photo (all skippable).
3. **First products:** up to three quick rows (name, price, optional stock), or **Add
   sample products** for your kind of shop. Remove samples later from Products.
4. **Your team:** the shop code, a printable login card for staff, add staff inline.
5. **Keep your shop safe:** confirm the recovery codes are saved (required), or make a
   new set; the old codes stop working.
6. **Ready:** "Make your first test sale" opens Sell.

Setup resumes where it was left (`onboarding_step`); **Skip setup** is always there.
Then a **guided tour** points at each part of the menu (owners/admins on the dashboard;
staff on Sell: search, tap to add, cart and Charge, Deduct). **Help** (bottom of the
menu and the account menu) has ten short articles, search, and "Take the tour again".
`docs/DEPLOY.md` explains free self-hosting on Cloudflare step by step.

**Proven by tests (351):** setup steps stay in range and only admins can move them;
recovery codes: 10 new ones, the old ones refused, logged, owner only; samples follow
the kind of shop, come once, and removal deletes unsold samples but archives sold ones
(their sales intact) without touching real products.

**Notes:** the tour's "seen" flag is kept per person on each device (localStorage), so
it can show once more on a new phone. Two-step login (2FA) is mentioned in setup as
coming later; it is not built yet. There is no staff password reset yet: the FAQ says to
deactivate and re-add.

## Phase 8 — PWA and offline (2026-10-31)

**Demo:** on a deployed (HTTPS) copy, open bls POS on a phone: **Install app** (Android)
or **Share → Add to Home Screen** (iPhone). It opens full screen with the bls icon.

1. Load **Sell** once online, then turn on airplane mode.
2. The header shows **Offline**; Sell says prices and stock are as of the last load.
3. Ring up a sale: the receipt says the number comes when back online, and stock counts
   down on the screen. The header shows "Offline · 1 unsent".
4. Turn the internet back on: the sale is sent by itself, gets its number, and shows on
   the dashboard. **Sales → On this device** lists anything still waiting or refused.

**How it works:** `public/sw.js` caches the app shell and built files (network first for
pages) and product photos already seen; it never caches API data. The app keeps its own
copy of the signed-in session and the product list (no costs) in IndexedDB, refreshed
on every online load. Offline sales go into an IndexedDB queue with their idempotency
key and `clientCreatedAt`; `src/shared/offline-sync.ts` sends them oldest first, stops
when still offline or signed out, and moves refused sales to **Needs review** (retry, or
an admin discards with a confirmation). Logout clears all offline data, after warning
about unsent sales. Icons are generated from `public/logo.svg` with `pnpm icons`.

**Proven by tests (357):** oldest first; a sale whose answer was lost is never recorded
twice; an out-of-stock sale goes to review while the others still send; a still-offline
or signed-out device keeps its sales in order; synced sales show in the income report.

**Notes:** the manifest uses the bls name and icon for every shop (a per-shop manifest
would need a signed-in route; the header and colors still follow the shop). A synced
sale counts on the day it reached the server; the device time is kept as
`client_created_at`. The service worker runs only in production builds, so offline
start-up is untested until the first deploy.

## Phase 9 — Security hardening (2026-10-31)

**Demo (as the owner):**

1. **My profile:** change your password; turn on **two-step login** (scan the QR code
   with Google Authenticator or similar, enter the code); see **where you're logged in**
   and log out other devices. Log out and back in: the code is asked after the password.
2. **Staff → Manage:** reset someone's password (new temporary one, shown once), make
   them admin or staff, or deactivate them. Each signs that person out.
3. **Dashboard:** a red notice appears if an account is locked after wrong passwords.
4. **Activity → Check the log:** your browser re-checks the hash chain and says the log
   is intact (or which entry was changed or removed).
5. **Shop page → Delete shop:** type the shop code and password; the shop closes at once
   and is erased after 30 days.
6. `/privacy` and `/terms` are linked from login and signup.

**Under the hood:** security headers on the app (`public/_headers`) and API; Origin
check on every change; TOTP (RFC 6238) with secrets AES-GCM encrypted under
`TOTP_ENC_KEY`; hourly cron seals activity entries into a per-shop hash chain and backs
up that hour's shops to private R2 (14 days, data built as JSON by D1 to fit the free
CPU limit); nightly job erases shops deleted 30+ days ago; Dependabot and a CI
`pnpm audit` gate; Playwright end-to-end tests (sale, cashier login, offline sale and
sync) on phone and desktop sizes, in CI. `docs/SECURITY.md` has every §7 item checked
except GitHub's secret scanning (an owner setting); `docs/THREAT_MODEL.md` lists threats,
controls, accepted risks and a review checklist.

**Proven by tests (389 API + 6 end-to-end):** headers on every answer; cross-site changes
refused; RFC 6238 vectors; login needs the code once on; password change, reset and role
change sign people out; admins can't touch the owner or promote; sessions list scoped
to you; backups private, without secrets, kept 14 days; sealed log entries changed,
removed or re-hashed are caught; shop deletion closes at once and erases everything
after 30 days without touching other shops.

**Notes:** turn on GitHub secret scanning and push protection (repository settings).
The privacy policy, terms and receipt wording need a lawyer's and tax professional's
review before offering bls POS to other businesses.
